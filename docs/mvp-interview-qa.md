# WASM Serverless 函数平台面试拷打 Q&A

本文用于准备 MiniCloud Local Core MVP 的项目面试，回答口径以简历中的项目描述和当前 MVP 的设计范围为准。

## 面试回答方式

面试时建议先用一句话说明作用，再根据面试官追问补充实现细节。例如不要一开始就说“通过 Discovery Epoch 和 Invocation Fence 保证一致性”，而是先说“防止旧 Worker 执行已经失效的函数版本”，面试官继续追问时再解释 Epoch 和 Fence 的具体字段。

下面的简明回答适合先回答问题，后面的详细问答用于应对继续追问。

## 简明版核心问答

### Q：这个项目是做什么的？

**简单回答：**

这是一个可以运行 WASM 函数的 Serverless 平台。开发者把函数编译成 WASM 上传，平台负责检查、发布和运行，其他人通过 HTTP 就可以调用。

### Q：WASM 在这里有什么用？

**简单回答：**

WASM 是函数的运行格式。它比完整服务更轻，启动快，而且默认不能随便访问服务器资源，所以适合运行用户上传的小函数。

### Q：用户怎么使用这个平台？

**简单回答：**

用户先写函数并编译成 `.wasm` 文件，然后上传并发布。发布完成后会得到一个 HTTP 地址，调用者像调用普通 API 一样发送请求即可，不需要安装函数运行环境。

### Q：这个平台解决了什么问题？

**简单回答：**

它把“写一段代码”和“让别人通过网络安全地使用这段代码”之间的部署工作统一处理了，包括版本、路由、超时、隔离和资源回收。

### Q：为什么不直接写一个 Gin 服务？

**简单回答：**

Gin 需要自己维护一个长期运行的服务进程。MiniCloud 只需要上传函数，平台负责启动和回收函数实例。两者都可以通过 HTTP 调用，但 Gin 管理的是完整服务，MiniCloud 管理的是独立函数。

### Q：Validator 是干什么的？

**简单回答：**

Validator 就像函数的“入场检查员”。它在函数运行前检查 WASM 文件是否有效、格式是否符合平台要求，检查通过后函数才能发布运行。

### Q：为什么 Validator 要单独运行？

**简单回答：**

因为上传的 WASM 文件是不可信的。把检查过程放到独立子进程中，即使文件有问题，也不会直接影响平台主进程。

### Q：Worker 是干什么的？

**简单回答：**

Worker 是真正执行 WASM 函数的节点。Gateway 收到请求后找到 Worker，Worker 创建一次独立的函数实例，执行完成后返回结果。

### Q：为什么每次调用都创建新的函数实例？

**简单回答：**

为了避免上一次请求留下的数据影响下一次请求。编译结果可以复用，但每次调用的内存和运行状态都是独立的。

### Q：编译缓存解决什么问题？

**简单回答：**

WASM 第一次运行需要编译，编译比较耗时。平台缓存已经编译好的模块，后续调用可以直接使用，同时仍然为每次请求创建新的运行实例。

### Q：Gateway 是干什么的？

**简单回答：**

Gateway 是平台的 HTTP 入口。它负责检查请求、验证身份、限制流量、找到正确版本，然后把请求交给 Worker 执行。

### Q：Function、Version 和 Route 有什么区别？

**简单回答：**

Function 是函数名称，Version 是这个函数的一份不可修改的代码版本，Route 决定请求当前应该访问哪个 Version。

例如：

```text
Function: text-clean
Version:  version-001
Route:    text-clean -> version-001
```

### Q：CAS 是什么？

**简单回答：**

CAS 可以理解为“先确认版本没变，再修改”。如果两个人同时修改同一个资源，后提交但使用旧版本号的请求会被拒绝，避免覆盖别人的更新。

### Q：这个项目有什么实际用途？

**简单回答：**

它适合把图片压缩、文本清洗、格式转换、Webhook 处理、规则判断和文件校验等小功能发布成 HTTP API，其他程序只需要请求 URL，不需要安装这些功能的运行环境。

### Q：项目最大的技术难点是什么？

**简单回答：**

难点不是执行一个 WASM 文件，而是保证只有经过校验、版本正确、Worker 状态正常并且授权有效的函数才能被调用。项目通过版本、快照、Worker Session 和调用前校验解决了这些问题。

### Q：这个项目和 gRPC 怎么选择？

**简单回答：**

WASM 函数适合独立、短时、需要隔离和按需运行的逻辑；gRPC 适合长期运行的服务之间进行高频、低延迟、强类型通信。两者可以一起使用，WASM 负责执行函数，gRPC 负责内部服务通信。

### Q：Function、Version、Deployment 和 Route 为什么要分开？

**简单回答：**

Function 是函数的名字，Version 是某一份确定的代码，Deployment 是这份代码应该怎样运行，Route 是请求应该发给哪个版本。

把它们分开后，代码版本可以保持不变，运行配置和流量入口也可以单独检查，不会因为修改路由而直接修改函数代码。

### Q：为什么 Version 不能直接修改？

**简单回答：**

因为正在运行的代码如果可以随时改变，就很难判断一次请求到底执行了哪个版本，也很难回滚。

所以发布后的 Version 不再修改。需要更新时创建新 Version，再把 Route 切换过去。

### Q：Artifact 为什么要用 SHA-256？

**简单回答：**

SHA-256 可以看成文件的指纹。上传时生成指纹，之后每次读取都重新检查指纹，确认文件没有被替换或损坏。

同时，相同内容会得到相同地址，可以避免重复保存同一个 WASM 文件。

### Q：Worker 是什么？

**简单回答：**

Worker 就是真正干活的执行节点。Gateway 收到请求后不会自己执行 WASM，而是把请求交给 Worker；Worker 负责加载代码、创建运行实例、执行并返回结果。

### Q：为什么需要 Worker Session？

**简单回答：**

Worker 每次重启后，虽然名字可能没变，但实际上已经是一个新的进程。Session 用来区分“这次启动的 Worker”和“上次启动的 Worker”。

这样旧 Worker 的心跳和旧请求到达后，平台可以识别出来并拒绝。

### Q：Worker 排空是什么意思？

**简单回答：**

Worker 要退出时，不能马上杀掉它，因为它可能还有正在执行的请求。

排空就是先停止接收新请求，等待旧请求执行完，确认没有任务后再退出，避免发布或重启时直接中断调用。

### Q：Gateway 为什么需要 Serving Snapshot？

**简单回答：**

Gateway 需要同时知道函数是否启用、访问认证是什么、Route 指向哪个版本，以及哪个 Worker 已经准备好。

Serving Snapshot 就是把这些信息打包成一份完整快照。Gateway 只使用这份快照，避免分别读取多个对象时拼出互相矛盾的状态。

### Q：Serving Authorization 是什么？

**简单回答：**

它可以理解为 Worker 执行一次函数前拿到的“内部通行证”。通行证会说明允许哪个 Worker、哪个函数版本和哪一代部署来执行。

如果 Worker 重启了、版本变了或通行证过期，Worker 就会拒绝执行旧请求。

### Q：CAS 是怎么解决并发修改的？

**简单回答：**

客户端读取资源时会拿到一个版本号。更新时必须带上这个版本号，平台确认资源没有被别人修改过后才允许更新。

如果别人已经先更新了资源，版本号就不匹配，当前请求会失败，而不会覆盖最新状态。

### Q：操作幂等有什么用？

**简单回答：**

网络请求可能已经成功，但客户端没有收到响应，于是客户端会重试。幂等账本可以识别“这是同一个操作”，直接返回第一次操作的结果，不会重复创建资源。

### Q：函数从上传到调用经过哪些步骤？

**简单回答：**

```text
编译成 WASM
  -> 上传并校验文件
  -> 创建函数版本
  -> Validator 检查
  -> 准备 Deployment
  -> 发布 Route
  -> Worker 加载函数
  -> Gateway 提供 HTTP 地址
  -> 用户发送请求
```

其中任何一步失败，平台都会停止继续发布，不会把一个没有准备好的函数暴露给用户。

### Q：用户调用函数时发生了什么？

**简单回答：**

用户只需要请求一个 URL。Gateway 先检查身份和请求限制，然后找到正确版本和 Worker；Worker 创建一个新的函数实例，执行完成后把结果返回给 Gateway，最后 Gateway 返回 HTTP 响应。

用户不需要知道 WASM 文件放在哪里，也不需要安装 Wazero。

### Q：为什么不让函数自己启动 HTTP Server？

**简单回答：**

如果每个函数自己启动 HTTP Server，就要自己处理端口、进程、超时、并发和关闭。

MiniCloud 统一提供 HTTP Gateway，函数只处理业务输入和输出，平台负责运行环境，这样发布小功能会更简单。

### Q：这个项目为什么先做单 Controller、单 Worker？

**简单回答：**

MVP 先验证最重要的事情：函数能不能安全地上传、发布、路由和调用。

如果一开始就加入多 Controller、Raft 和多 Worker，问题会同时变成分布式系统问题，难以判断到底是函数链路还是集群链路出了错。单机版本先把核心流程跑通，再扩展集群更稳妥。

### Q：本机直接调用函数和通过 MiniCloud 调用有什么区别？

**简单回答：**

同一个项目里的普通函数调用更快，也更简单。MiniCloud 的优势不是本机性能，而是把函数独立出来，提供版本管理、HTTP 调用、权限控制、超时和隔离。

如果只是内部工具，直接调用就够了；如果希望其他程序、其他电脑或不可信代码使用它，MiniCloud 更合适。

### Q：WASM 和 gRPC 分别适合什么场景？

**简单回答：**

WASM 适合短时间、输入输出清楚、需要隔离和按需执行的小函数，例如文本处理、图片转换和 Webhook 处理。

gRPC 适合两个长期运行的服务之间高频通信，例如订单服务调用库存服务。它们可以一起使用：WASM 负责运行函数，gRPC 负责内部服务之间的通信。

## 一、项目概览

### Q1：请你先用一分钟介绍一下这个项目。

**参考回答：**

这是一个基于 Go 和 Wazero 开发的 WASM Serverless 函数平台。用户把函数编译成 WASM 后上传，平台负责检查、发布、路由和执行，其他人通过 HTTP 就能调用这个函数。

简单说，用户只需要写业务逻辑，平台负责处理函数怎么运行、运行多久、能使用哪些资源，以及请求应该交给哪个 Worker。当前 MVP 采用单 Controller、单 Worker 的本地模式，先保证从函数发布到 HTTP 调用的完整流程。

### Q2：为什么选择 WASM，而不是容器或直接运行 Go 插件？

**参考回答：**

如果直接运行 Go 插件，插件出问题可能影响主程序，而且权限边界也不清楚；使用容器虽然隔离更完整，但启动和管理成本更高。

WASM 可以把函数放进一个受控的运行环境中。函数默认不能随便访问服务器文件和系统资源，平台还可以限制它的运行时间和输入输出，所以比较适合运行独立的小功能。

### Q3：这个项目和普通 WASM Runtime 的区别是什么？

**参考回答：**

Wazero 只负责把 WASM 文件跑起来。这个项目在 Wazero 外面增加了上传、版本、路由、Worker、认证和限流等功能。

可以简单理解为：Wazero 负责“执行代码”，MiniCloud 负责“把代码发布成别人可以调用的函数服务”。

## 二、WASM 与执行模型

### Q4：你的 WASM 函数是怎么被调用的？

**参考回答：**

项目把 HTTP 请求转换成统一的 WASM 请求格式，通过标准输入传给函数；函数处理后把结果写到标准输出，平台再把结果转换成 HTTP 响应。

这样不同语言编译出来的 WASM 函数，都可以按照同一套输入输出规则运行。

调用过程是：

```text
HTTP Request
  -> Gateway 认证与限流
  -> 路由选择
  -> Worker 授权校验
  -> 创建 Guest Instance
  -> WASM stdin/stdout ABI
  -> HTTP Response
```

### Q5：为什么采用 stdin/stdout，而不是直接调用 WASM 导出函数？

**参考回答：**

使用标准输入输出的好处是简单，而且 Go 等语言比较容易生成这种 WASM 程序。平台可以统一检查输入和输出大小，也不用为每种语言单独设计调用方式。

它会有一些编码和解码开销，但对于当前 MVP 来说，协议清楚、实现稳定比追求复杂的组件组合更重要。

### Q6：每次请求会复用 WASM 实例吗？

**参考回答：**

不会复用函数实例。每次请求都会创建一个新的运行实例，用完就销毁，这样上一次请求留下的数据不会影响下一次请求。

平台只复用已经编译好的模块，既减少重复编译，又保持每次调用的运行状态独立。

### Q7：编译缓存缓存的是什么？为什么不会造成状态污染？

**参考回答：**

缓存的是已经编译好的只读模块，不是上一次请求的运行现场。

平台只有在代码版本和运行配置都相同的情况下才复用缓存；每次请求仍然使用新的实例，所以不会共享函数状态。

### Q8：WASM 函数访问宿主机文件或环境变量怎么办？

**参考回答：**

MVP 默认不允许函数访问宿主机资源。函数不会自动拿到服务器的环境变量、文件和参数；如果将来要开放某种能力，也必须由平台明确配置。

平台也不会把服务器密钥或敏感环境变量传给函数。

## 三、安全与稳定性

### Q9：为什么还要设计独立 Validator 子进程？WASM 本身不是沙箱吗？

**参考回答：**

WASM 本身能限制函数访问宿主资源，但上传的文件仍然需要被解析和编译。Validator 把这一步放到独立子进程里，即使文件有问题，也不会直接拖垮平台主进程。

Validator 只返回检查结果，不负责运行用户的业务函数。

### Q10：函数死循环时，平台如何处理？

**参考回答：**

每次调用都有明确的超时时间。函数一直不返回时，平台会取消这次调用，释放它占用的资源，并向调用方返回超时错误。

这样一个死循环函数不会一直占用 Worker。

### Q11：函数输出超限时怎么办？

**参考回答：**

平台会限制请求大小、函数返回结果大小和日志大小。超过限制时会拒绝或终止这次调用，不会让函数无限输出把 Worker 或网络资源耗尽。

### Q12：如何防止恶意或错误函数影响其他请求？

**参考回答：**

主要有四层控制：

1. 函数默认不能随便访问宿主机。
2. 每次调用使用独立实例。
3. 平台限制超时、并发、队列、输入输出和日志大小。
4. 函数运行前先经过独立 Validator 检查。

因此异常函数最多影响当前调用和它占用的受控资源，不会直接共享其他请求的 Guest 状态。

## 四、函数发布与数据模型

### Q13：Function、Version、Deployment 和 Route 分别是什么？

**参考回答：**

- `Function` 是用户看到的函数名称，例如 `hello`。
- `Version` 是这段函数代码的一份固定版本。
- `Deployment` 描述这份代码要用多少资源、以什么方式运行。
- `Route` 决定请求应该发给哪个 Version。

这种拆分可以避免直接修改正在运行的版本，也可以让发布、部署和流量路由分别进行校验。

### Q14：为什么 Artifact 要使用 SHA-256 内容寻址？

**参考回答：**

SHA-256 可以看成 Artifact 的文件指纹。上传和读取时都检查这个指纹，就能确认文件没有被替换或损坏。

相同内容会得到相同地址，因此可以去重；Version 只引用这个地址，发布后代码内容不会被悄悄修改。

### Q15：Version 为什么不能原地修改？

**参考回答：**

如果 Version 可以直接修改，同一个版本名在不同时间可能对应不同代码，请求结果就无法复现，回滚也不可靠。

所以发布后的 Version 不再改动。需要更新时创建新 Version，再把 Route 切换过去。

### Q16：Deployment Generation 的作用是什么？

**参考回答：**

Generation 可以理解为一次部署配置的版本号。它把代码版本、资源限制和运行状态绑定在一起。

部署配置发生重要变化时生成新的 Generation，Worker 就能识别并拒绝仍然使用旧配置的请求。

## 五、Worker、Gateway 与授权

### Q17：Worker Registry 解决什么问题？

**参考回答：**

Registry 就像 Worker 的通讯录和健康档案，记录它是否在线、能处理什么、还有多少容量，以及当前是否正在排空。

MVP 虽然只有一个本地 Worker，但仍然按这个方式记录状态，后续增加多个 Worker 时可以直接复用。

### Q18：为什么需要 Worker Session，而不仅是 Worker ID？

**参考回答：**

Worker ID 只能说明“是哪台 Worker”，Session 才能说明“是哪一次启动”。Worker 重启后会得到新的启动标识。

这样旧进程发来的心跳或请求就不会被新进程误认为有效。

### Q19：Worker 排空是怎么实现的？

**参考回答：**

Worker 要退出时先进入 Draining，不再接收新任务，但会把已经开始的调用做完。等没有活动调用后，才真正退出。

这样可以避免重启或发布时直接中断正在执行的函数。

### Q20：Gateway 为什么不能直接读取 Controller 状态？

**参考回答：**

Gateway 不能分别读取 Function、Route 和 Worker 状态，因为读取过程中可能发生变化，最后拼出一套互相矛盾的配置。

Serving Snapshot 就是平台提前整理好的一份完整服务视图。Gateway 只使用这份视图，不自己拼接状态。

### Q21：Serving Authorization 解决什么问题？

**参考回答：**

它可以理解为 Worker 执行函数前拿到的一张内部通行证，通行证会绑定：

- Worker Session
- Assignment ID
- Version Admission Epoch
- Deployment Generation
- Policy Digest
- Discovery Epoch

如果 Worker 已重启、部署配置变了或通行证过期，Worker 会在真正执行函数前拒绝调用。

### Q22：Gateway 调用失败时会不会自动重试？

**参考回答：**

同步调用默认不自动重试。Gateway 在选择 Route Target 和 Endpoint 后只执行一次调用，失败直接返回错误。

这样可以避免同步函数产生重复副作用，也让调用方明确知道本次执行是否成功。异步至少一次、幂等键和重试策略属于另一种调用语义，不能和同步调用混在一起。

## 六、并发、一致性与幂等

### Q23：Resource Revision CAS 是什么？

**参考回答：**

客户端更新资源时必须带上自己读取到的 Resource Revision。服务端只有在当前 Revision 仍然匹配时才允许更新，成功后 Revision 加一。

例如客户端基于 Revision 3 修改资源，但另一个请求已经更新到 Revision 4，那么前一个请求会收到 `revision_conflict`，不会覆盖新状态。

### Q24：Route CAS 解决什么问题？

**参考回答：**

Route 是流量入口，错误更新可能让请求切到错误版本。因此 Route 发布也使用独立的 Route Revision CAS。

并发发布同一个 Function 的两个 Route 时，只有持有最新 Revision 的请求可以成功，另一个请求会失败，不会产生部分 Route 状态。

### Q25：操作幂等和资源 CAS 有什么区别？

**参考回答：**

CAS 解决的是“更新时状态是否过期”；操作幂等解决的是“同一个客户端操作是否已经执行过”。

例如网络超时后客户端重试同一个 `operation_id`，幂等账本可以返回第一次操作的结果；如果相同 `operation_id` 搭配了不同请求摘要，则返回冲突，防止 ID 被复用执行另一种操作。

## 七、MVP 架构取舍

### Q26：为什么 MVP 只使用单 Controller 和单 Worker？

**参考回答：**

MVP 的目标是先验证函数从发布、校验、部署、路由到执行的完整链路，而不是同时解决分布式共识和故障恢复。

单 Controller、单 Worker 可以减少网络、Raft、节点发现和跨进程调试带来的复杂度，同时保留控制命令、Session、Serving Snapshot、Assignment 和授权等边界，为后续扩展多节点保留结构。

### Q27：单 Controller 会不会让项目失去 Serverless 的意义？

**参考回答：**

不会。Serverless 的核心是用户不需要管理函数运行实例，由平台负责发布、路由、资源控制和执行。高可用控制面属于平台可靠性扩展，不是 Serverless 定义本身。

MVP 先证明函数执行平台的核心闭环，后续再把单 Controller 替换为 Raft 控制面，把单 Worker 替换为多 Worker 调度。

### Q28：为什么不直接使用 Docker？

**参考回答：**

Docker 更适合承载完整服务和长期运行进程，而这个项目关注的是函数级快速启动、低资源执行和细粒度能力控制。

MVP 采用 WASM Instance 作为一次调用的执行边界，编译模块可以缓存，Guest Instance 可以快速创建和销毁，适合短时同步函数调用。

### Q29：当前 MVP 的核心验收路径是什么？

**参考回答：**

核心路径是：

```text
创建 Function 和默认 Trigger
  -> 上传 WASM Artifact
  -> 创建不可变 Version
  -> Validator 隔离校验
  -> 生成 Deployment Generation 1
  -> 发布 10000 权重 Route
  -> Gateway 应用 Serving Snapshot
  -> Worker 创建 Guest Instance
  -> 返回 HTTP 结果
```

同时验证非法模块会进入可查询的 Failed 状态，过期 Function 或 Route 写入会被 CAS 拒绝，认证失败和资源超限会返回稳定错误。

## 八、深挖与反问

### Q30：这个项目最难的地方是什么？

**参考回答：**

一句话说，难点不是“能不能运行函数”，而是“任何一次运行都必须使用正确的版本、正确的 Worker 和正确的权限”。

最难的不是启动一个 WASM 模块，而是定义清楚跨组件的状态边界和失败语义。

例如，一个 Version 只有在 Artifact 已成功写入、Validator 已通过、运行时 Profile 匹配并且 Deployment Policy 有效后，才能进入 Ready；Gateway 也不能只看到一个 Route 就调用，还必须看到匹配的 Endpoint、Assignment 和 Serving Authorization。

因此项目中大量工作集中在状态转换、CAS、快照、Fence、Session 和错误码，而不是单纯的函数执行。

### Q31：如果让你继续优化，你会优先优化哪里？

**参考回答：**

我会先让系统更容易观察和定位问题：知道一次请求到底慢在编译、排队、实例创建还是函数本身。

我会优先完善端到端观测和性能基准，重点测量 Validator 校验、WASM 编译、缓存命中、实例化和函数执行各阶段的耗时，并为每次调用记录 Request ID、Invocation ID、Version、Worker、Route Revision 和结果状态。

这样可以判断延迟究竟来自冷编译、缓存未命中、Worker 排队还是 Guest 本身，而不是只看到一个总耗时。

### Q32：你如何证明项目不是只能跑 Happy Path？

**参考回答：**

不只测试“正常函数能返回结果”，还专门测试各种异常输入、超时、旧状态和并发冲突，确认系统出错后仍然能恢复。

测试覆盖了非法 WASM、摘要不匹配、输出超限、超时、Guest Panic、旧 Session、心跳过期、Worker 排空、过期 CAS、重复操作、认证失败、限流和空 Serving Snapshot 等拒绝路径。

这些测试验证的不只是函数能否返回结果，也验证了错误发生后资源是否释放、状态是否保持一致以及后续调用是否仍然可用。

## 九、面试时应主动强调的边界

### Q33：这个项目的核心价值是什么？

**参考回答：**

简单说，项目把一段 WASM 代码变成了一个可以安全发布、按版本管理并通过 HTTP 调用的函数服务。

核心价值是把 WASM Runtime 封装成一个具备发布、路由、授权和资源控制能力的函数平台，而不是简单调用 Wazero API。

项目同时保留了后续分布式演进所需要的控制面边界，例如版本化命令、Resource Revision、Worker Session、Serving Snapshot 和 Invocation Fence，使 MVP 的简化不会破坏后续扩展方向。

### Q34：如果面试官只记住三件事，你希望是哪三件？

**参考回答：**

我希望面试官记住：它能安全运行别人上传的函数，能完成从上传到 HTTP 调用的完整流程，还能防止旧版本和并发更新造成错误。

第一，项目解决了不可信 WASM 函数的安全执行问题；第二，完成了从制品校验、版本发布到 HTTP 调用的 Serverless 核心链路；第三，通过 Session、快照、Fence 和 CAS 处理了并发更新、旧 Worker 和过期授权等边界问题。

## 十、项目难点与解决思路

### Q35：项目中最难的技术问题是什么？

**参考回答：**

通俗地说，难点是不能让一个“看起来已经发布”的函数在实际运行时使用错误的代码、错误的 Worker 或过期权限。

最难的不是把 WASM 模块跑起来，而是保证从控制面状态到实际执行之间没有出现“看起来可用、实际不安全”的中间状态。

例如，Route 已经发布并不代表可以调用。还必须同时满足 Version 已通过校验、Deployment Policy 匹配、Worker Replica 已 Ready、Assignment 身份正确、Serving Authorization 已安装，并且这些信息必须来自同一个一致的 Serving Snapshot。

项目的主要难点集中在状态边界、并发更新、旧 Session、资源释放和失败后的可重试性。

### Q36：为什么不能分别读取 Function、Version、Route 和 Worker 状态？

**参考回答：**

因为这些信息可能在读取过程中变化。分别读取时，Gateway 可能把新旧状态拼在一起，得到一套实际上不存在的配置。

如果 Gateway 依次读取这些对象，中间可能发生 Route 发布或 Worker Session 切换，最后拼出来的状态可能来自不同时间点。

例如：Function 已经切到新版本，但 Route 仍是旧版本；或者 Route 已经指向某个 Version，但 Worker 仍然是旧 Deployment Generation。这样的组合不能用于执行函数。

因此项目使用 Serving Snapshot，把 Function、Trigger、Route 和 Ready Endpoint 作为一个完整视图发布。Gateway 只消费完整快照，不能自行拼接控制面数据。

### Q37：Serving Snapshot 是怎么保证安全的？

**参考回答：**

可以把它理解成发布前做好的完整检查单：只有代码、部署、Worker 和权限全部对应上，Gateway 才会看到这个 Endpoint。

快照只有在以下身份全部匹配时才会包含 Endpoint：

- Route Target 的 Version 和 Generation
- Assignment 身份
- Worker Session
- Ready Replica
- Worker 当前调度意图
- Serving Authorization

快照还会进行规范化排序和摘要计算，使用 Discovery Epoch 和 Serving Sequence 防止旧快照回放、顺序倒退或增量事件出现间隙。

### Q38：为什么 Worker Reconcile 不能直接在构建快照时执行副作用？

**参考回答：**

因为整理“当前可用状态”和真正启动、关闭 Worker 是两件事。把它们混在一起，前一步失败时可能留下半完成的结果。

构建快照的职责应该是观察状态，不能一边生成快照一边 Prepare Replica、安装授权或取消旧 Replica。

如果快照发布失败，就会出现 Replica 已经准备好但快照没有生效的情况；如果快照发布成功前就取消旧 Replica，又可能造成服务中断。

所以项目把流程拆成两个阶段：Reconciler 负责准备和收敛 Worker 状态，Snapshot Builder 只读取已经安装成功的结果。这样失败时可以分别重试，不需要实现复杂的跨组件 Begin/Commit/Abort 事务。

### Q39：编译缓存为什么比普通 LRU 更复杂？

**参考回答：**

普通缓存只关心有没有缓存；这里还要关心同一份代码是否正在编译、是否正在使用、等待者取消后能否安全退出，以及 Worker 关闭时能否收干净。

普通 LRU 只需要考虑命中和淘汰，但 WASM 编译缓存还要解决几个问题：

1. 相同 Version 的并发冷启动只能编译一次。
2. 不同 Version 的冷启动必须有并发和队列上限。
3. 调用期间被使用的编译模块不能被淘汰。
4. 某个等待者取消不能影响其他等待者。
5. 关闭 Worker 时必须等待所有 Lease 和编译任务退出。

因此项目使用共享加载任务、Lease、独立等待者取消和有界冷加载队列，避免重复编译、无限排队和使用中的模块被提前释放。

### Q40：为什么缓存 Key 必须包含 Runtime Profile？

**参考回答：**

同一个 WASM 文件在不同运行环境下编译出来的结果可能不同，所以不能只用文件摘要判断缓存能否复用。

相同 WASM Artifact 在不同 Runtime、编译器、WASI ABI、WASM Feature 或内存档位下，生成的编译结果不一定兼容。

因此缓存 Key 不只包含 Artifact Digest，还包含 Runtime Name、Runtime Version、Engine、ABI、Host API Profile、Feature Profile、内存档位和目标平台。这样可以避免错误复用旧编译结果。

### Q41：Worker Session 解决了什么实际问题？

**参考回答：**

它解决的是“旧 Worker 重启后发来的消息不能继续生效”。Worker ID 只能认出是哪台 Worker，Session 才能认出是哪一次启动。

Worker ID 只能表示逻辑节点，不能区分同一个节点重启前后的两个进程。

项目为每次启动生成 Boot ID 和递增 Session Epoch。旧进程的心跳、Assignment 和授权即使晚到，也会因为 Session 不匹配而被拒绝。这样可以避免旧 Worker 重连后污染新 Worker 的状态。

### Q42：为什么项目中大量使用 monotonic clock？

**参考回答：**

它是用来可靠计算“经过了多久”，避免系统时间被调整后把已经过期的心跳或授权误判成有效。

心跳超时、授权 TTL 和 Snapshot 过期判断都不应该依赖墙上时间。系统时间可能因为 NTP 校准或人工调整而回拨，直接使用墙上时间可能让已经过期的授权重新变得有效。

项目使用可注入的单调时间进行间隔判断。如果检测到时钟回退，会进入 fail-closed 状态，把相关 Worker 标记为不可用，而不是继续放行不确定的请求。

### Q43：为什么本地 MVP 也要保留 Session、Fence 和 Discovery Epoch？

**参考回答：**

这些字段提前规定了“旧状态不能执行”的规则。虽然单机 MVP 暂时简单，但以后增加多个 Worker 时不需要重新设计安全边界。

虽然 Local Core 只有一个 Controller 和一个 Worker，但这些字段定义的是跨组件的安全语义，而不是单纯的集群实现细节。

如果 MVP 直接省略这些边界，后续扩展成多 Worker 或网络 RPC 时很可能需要重写调用协议。现在保留它们，可以在单进程内验证身份匹配、旧状态拒绝和快照传播，之后再替换传输层和控制面实现。

### Q44：为什么 Artifact 需要在多个边界重复校验摘要？

**参考回答：**

同一个文件会经过上传、存储、校验和执行多个环节。每个环节重新核对指纹，可以尽早发现文件被替换或损坏。

不同阶段面对的信任边界不同。上传时校验的是客户端提交的内容，Validator 校验的是待编译内容，Worker 加载时校验的是本地或远端实际读取的字节。

每个边界都重新检查摘要、长度和元数据，可以防止文件在存储、复制或加载过程中被替换或损坏。重复校验的成本低于执行错误的函数版本。

## 十一、名词解释

### Q45：WASM 是什么？

**参考回答：**

可以把 WASM 理解成一种“通用的函数安装包格式”。函数不直接绑定某台机器，而是交给支持 WASM 的运行器执行。

WASM，也就是 WebAssembly，是一种可移植的二进制指令格式。C、Rust、Go 等语言可以编译成 WASM，然后交给浏览器或服务器 Runtime 执行。

它本身不等于完整操作系统，也不会自动获得文件和网络权限。宿主程序需要通过 WASI 或其他接口显式授予能力。

在本项目中，WASM 是用户上传的函数程序，Wazero 是负责执行它的 Runtime。

### Q46：WASI 是什么？

**参考回答：**

WASI 可以理解成 WASM 和外部世界之间的“插座规范”，规定函数如何读输入、写输出，以及在宿主允许时访问文件或时间等能力。

WASI 是 WebAssembly System Interface，为 WASM 提供标准化的系统接口，例如命令行参数、标准输入输出、时钟和文件访问。

项目使用 WASI Command 模式，把一次 HTTP 函数请求编码到标准输入，把函数结果从标准输出读取出来。

### Q47：Wazero 是什么？

**参考回答：**

Wazero 是真正把 WASM 跑起来的 Go 库，但它本身不是完整的发布平台。

Wazero 是 Go 实现的 WebAssembly Runtime，可以直接嵌入 Go 程序，不依赖额外的系统级 Runtime 进程。

在项目中，Wazero 负责模块编译、实例化、WASI 绑定和 Guest 执行；项目在它之上增加 Validator、Worker、缓存和 Gateway 等平台能力。

### Q48：Validator 是什么？

**参考回答：**

Validator 就像函数上线前的“安检员”：先确认文件能不能运行、是否符合平台规则，再允许它进入发布流程。

Validator 是 WASM Artifact 的准入校验器。它在函数正式部署前检查模块格式、ABI、导入导出、内存和 Runtime Profile 是否符合平台要求，并返回结构化报告。

项目把 Validator 放到独立子进程中，避免不可信模块的解析和编译直接运行在 Controller 或 Management API 进程里。

### Q49：Artifact 是什么？

**参考回答：**

Artifact 就是上传到平台的那份不可修改的 WASM 文件及其身份证明，不是源代码仓库，也不是一个可随意覆盖的文件名。

Artifact 是用户上传的 WASM 二进制及其摘要、大小和元数据。项目通过 SHA-256 内容寻址保存 Artifact。

它类似于函数发布时的不可变构建产物，Version 通过 Digest 引用它，而不是依赖一个可以被覆盖的文件名。

### Q50：Guest Instance 是什么？

**参考回答：**

Guest Instance 可以理解成“某一次请求临时开出来的函数房间”。请求结束后房间被清理，下一次请求使用新的房间。

Guest Instance 是一次 WASM 调用对应的运行实例。它包含本次调用的线性内存、全局状态和执行上下文。

项目每次请求创建新的 Guest Instance，执行结束后释放；编译结果可以复用，但 Guest 状态不能跨请求复用。

### Q51：Worker 是什么？

**参考回答：**

Worker 就是实际干活的执行节点：它加载函数、创建运行实例、执行代码，并把结果交回 Gateway。

Worker 是实际运行 WASM 函数的执行节点。它负责加载 Artifact、使用编译缓存、准备 Replica、执行 Guest Instance、报告状态并处理心跳。

当前 MVP 使用一个本地 Worker，但 Worker 接口和 Session 模型支持后续扩展多节点。

### Q52：Gateway 是什么？

**参考回答：**

Gateway 是用户请求进入平台的前台。它先判断请求能不能进来、应该找哪个版本，再把任务交给 Worker。

Gateway 是用户请求进入平台后的入口层。它负责认证、限流、请求解析、Route 选择、Serving Snapshot 查询和 Worker 调用，不直接修改控制面状态。

这样可以把用户请求的数据面路径和 Function 发布等控制面操作分开。

### Q53：Serving Snapshot 是什么？

**参考回答：**

它是一张“当前哪些函数可以被调用”的完整清单，Gateway 直接查这张清单，不需要自己拼接很多零散状态。

Serving Snapshot 是 Gateway 使用的完整服务视图，包含 Function、Trigger、Route 和可以实际接收请求的 Ready Endpoint。

它不是某个单独持久化对象，而是控制面状态和 Worker 状态经过校验后的安全投影。Gateway 只依赖这个投影进行调用。

### Q54：CAS 是什么？

**参考回答：**

CAS 的核心意思是“修改前先确认自己看到的还是最新状态”。如果别人已经改过，当前修改就停止，避免把新数据覆盖掉。

CAS 可以指两种相关概念。

在 Artifact Store 中，CAS 是 Content-Addressed Storage，即用内容摘要作为制品地址。

在 Function 和 Route 更新中，CAS 是 Compare-And-Swap，即只有当前资源 Revision 等于请求携带的预期 Revision 时才允许修改。

### Q55：Resource Revision 是什么？

**参考回答：**

它就是资源的版本号。客户端读取到版本 3，更新时就声明“我是在版本 3 的基础上修改”，如果服务端已经变成版本 4，更新会被拒绝。

Resource Revision 是资源自身的单调版本号。每次成功修改资源后递增，客户端更新时必须携带读取时的 Revision。

它用于识别过期写入，避免两个并发客户端互相覆盖。

### Q56：Deployment Generation 是什么？

**参考回答：**

它表示“这一套部署配置是第几版”。配置变了就换一个 Generation，旧 Worker 不会继续用旧配置接收请求。

Deployment Generation 表示一次完整的部署策略版本。它绑定 Version、资源限制、能力策略和副本运行身份。

当运行策略发生变化时，新的 Generation 可以让旧 Assignment 和旧授权失效，避免旧配置继续提供服务。

### Q57：Serving Authorization 和普通 Token 认证有什么区别？

**参考回答：**

普通 Token 判断“用户能不能访问”；Serving Authorization 判断“这个 Worker 能不能执行这一次具体的函数任务”。一个面向外部用户，一个面向内部执行节点。

普通 Token 认证解决的是“外部调用者有没有权限访问函数”。

Serving Authorization 解决的是“这个 Worker 是否被控制面允许执行这个具体 Assignment”。它绑定 Worker Session、Version、Deployment Generation 和 Discovery Epoch，是内部执行授权，不是用户登录凭证。

## 十二、这个项目执行函数有什么用

### Q58：这个平台实际可以用来做什么？

**参考回答：**

通俗地说，就是把自己写好的小功能发布成一个网址，别人发 HTTP 请求就能使用，不需要把代码复制到对方电脑上。

它可以把用户编译好的业务逻辑封装成独立函数，通过 HTTP 按需调用，而不要求用户管理函数进程、线程或机器。

例如：

- 图片压缩和格式转换
- 文本清洗和数据转换
- Webhook 接收与处理
- 轻量级鉴权和请求预处理
- 文件摘要、格式校验和内容分析
- 边缘节点上的规则计算
- 业务流程中的独立计算步骤

函数执行平台的价值在于，用户只需要关心输入、输出和业务逻辑，平台负责函数的校验、隔离、路由、超时和资源回收。

### Q59：为什么不让用户自己启动一个 HTTP 服务？

**参考回答：**

因为这样每个用户都要自己处理一整套运维工作；平台统一处理后，用户只需要关心函数本身。

让每个用户自己维护 HTTP 服务，会带来进程管理、端口分配、部署升级、健康检查、权限控制和资源隔离等问题。

Serverless 平台把这些通用能力集中处理，用户上传函数后即可获得统一的 HTTP 调用入口。

对于短时、低频或突发任务，平台还可以按调用创建 Guest Instance，避免长期运行大量空闲服务。

### Q60：这个项目和普通 RPC 服务有什么区别？

**参考回答：**

普通 RPC 更像“一个一直开着的服务电话”；这个平台更像“提交一个任务，平台按需开一个函数实例来执行”。

普通 RPC 服务通常由开发者自己维护常驻进程，平台主要负责网络通信。

这个项目把一次函数调用作为受控执行单元，平台还负责：

- 上传和校验代码
- 管理不可变版本
- 限制函数资源
- 创建和销毁 Guest Instance
- 处理路由和部署策略
- 控制函数对宿主机的能力访问

因此它更接近函数计算平台，而不是单纯的 RPC 框架。

### Q61：WASM Serverless 的实际优势是什么？

**参考回答：**

简单说，它用较小的运行成本换来“函数可以独立发布、按需运行、限制权限并且跨机器调用”。

第一，WASM 模块通常比完整容器镜像更轻，适合快速启动和边缘部署；第二，WASI 能力模型可以让平台以更细粒度控制函数能访问什么；第三，WASM 二进制具有较强的跨平台特性；第四，编译模块可以缓存，而 Guest Instance 仍然保持调用级隔离。

这使它适合运行短时、输入输出明确、需要快速启动和受控权限的函数。

### Q62：这个项目的业务价值怎么概括？

**参考回答：**

它把“我写了一个函数”变成“别人可以安全、稳定地通过 HTTP 使用这个函数”。

项目把“上传一段代码”和“安全地提供一个可调用函数”之间缺失的平台能力补齐了。

用户不需要管理执行进程和宿主资源，只需要提供 WASM 函数；平台负责制品完整性、版本不可变、请求路由、Worker 执行、权限检查、超时和故障边界。它适合作为轻量级函数计算、边缘计算或内部插件执行平台的基础。

## 十三、WASM 与 gRPC 的使用场景

### Q63：什么时候适合使用 WASM 函数平台？

**参考回答：**

当功能比较小、输入输出明确、不需要一直运行，并且希望平台帮忙处理隔离和部署时，就适合使用 WASM 函数平台。

当一段逻辑相对独立、输入输出边界清晰、需要按需执行，并且希望平台统一负责隔离、超时和发布时，适合使用 WASM 函数平台。

典型场景包括：

- Webhook 接收和事件处理
- 文本清洗、格式转换和数据脱敏
- 图片压缩、文件校验和内容分析
- 请求鉴权、参数校验和规则判断
- 边缘节点上的轻量计算
- 用户自定义插件或脚本的安全执行
- 不同业务系统之间的简单数据转换

这类功能通常不需要长期持有连接，也不需要自己维护完整的 HTTP 服务。开发者只需要编写函数、编译成 WASM、上传发布，然后通过 HTTP 调用。

### Q64：什么时候适合使用 gRPC？

**参考回答：**

当两个长期运行的后端服务需要频繁、快速、格式严格地互相调用时，适合使用 gRPC。

当两个长期运行的服务之间需要高频、低延迟、强类型的内部通信时，适合使用 gRPC。

典型场景包括：

- 用户服务调用订单服务
- 网关调用用户、库存或支付服务
- Controller 调用 Worker 的内部控制接口
- 多个微服务之间的稳定 RPC 通信
- 需要双向流或服务端流的场景
- 需要通过 Protobuf 统一约束接口和生成客户端代码的场景

gRPC 的前提通常是调用双方都维护一个长期运行的服务进程，服务需要自己处理连接、并发、生命周期和部署。

### Q65：WASM 和 gRPC 的调用方式有什么区别？

**参考回答：**

一句话区别：WASM 是先把函数发布到平台，再调用平台提供的 HTTP 地址；gRPC 是先启动一个长期运行的服务，再调用它定义好的接口。

WASM 函数平台的调用方式是：

```text
上传 WASM 函数
  -> 平台发布函数
  -> 获得 HTTP URL
  -> 请求 URL 并传入输入数据
  -> 平台创建 Guest Instance 执行
  -> 返回函数结果
```

例如：

```bash
curl -X POST http://localhost:8080/invoke/text-clean \\
  -H 'Content-Type: text/plain' \\
  -d '  hello    world  '
```

gRPC 的调用方式是：

```text
定义 .proto 接口
  -> 生成 Server 和 Client 代码
  -> 启动长期运行的 gRPC Server
  -> Client 调用指定 Service/Method
  -> Server 返回强类型消息
```

示例接口：

```protobuf
service TextService {
  rpc Clean(CleanRequest) returns (CleanResponse);
}
```

### Q66：WASM 和 gRPC 可以一起使用吗？

**参考回答：**

可以。WASM 负责“函数怎么被隔离和执行”，gRPC 负责“常驻服务之间怎么通信”，不是互相排斥的选择。

可以，而且两者解决的是不同层次的问题。

一种组合方式是：外部请求通过 HTTP 进入 MiniCloud，MiniCloud 负责路由、认证和 WASM 执行；WASM 函数需要访问内部业务服务时，再通过受控的 gRPC 或其他 Capability 调用后端服务。

另一种组合方式是：Controller、Gateway 和 Worker 之间使用 gRPC 进行高效的内部通信，而用户函数仍然以 WASM 形式运行。

可以简单理解为：

- WASM 解决“业务函数在哪里、以什么安全边界运行”。
- gRPC 解决“长期运行的服务之间如何高效通信”。

### Q67：为什么不直接用 gRPC 代替 MiniCloud？

**参考回答：**

因为 gRPC 只是通信方式，不会自动帮你管理函数的上传、版本、隔离、超时和回收。

gRPC 只解决服务之间的通信协议，不负责函数制品校验、版本发布、Guest 隔离、按调用创建实例、函数超时、路由发布和执行资源回收。

如果直接使用 gRPC，仍然需要自己维护一个长期运行的服务进程，并自行处理部署和隔离。MiniCloud 的价值是在 gRPC 或 HTTP 之上补充函数平台的生命周期和安全执行能力。

### Q68：如何选择 WASM 和 gRPC？

**参考回答：**

先看一个简单判断：独立的小函数选 WASM，长期运行的服务之间通信选 gRPC；两者都需要时就组合使用。

可以从四个问题判断：

1. 这段逻辑是否需要长期运行？不需要时优先考虑 WASM 函数。
2. 调用双方是否都是稳定的内部服务？是的话可以考虑 gRPC。
3. 是否需要强类型接口和高频低延迟通信？需要时 gRPC 更合适。
4. 是否需要隔离不可信代码、快速发布和按需执行？需要时 WASM 函数平台更合适。

最终的系统通常不是二选一，而是使用 WASM 承载业务函数，使用 HTTP 作为外部调用入口，使用 gRPC 作为内部服务通信协议。

## 十四、函数从编写到调用的完整链路

### Q69：请完整说明一个函数从编写到被调用的过程。

**参考回答：**

可以把它看成两段：先把函数上线，再让用户通过 URL 调用。用户只负责写函数和上传，平台负责后面的检查、部署和执行。

整个流程分为发布链路和调用链路。

发布链路是：

```text
编写 Go 函数
  -> 编译成 WASM
  -> 上传 Artifact
  -> 创建 Function/Version
  -> Validator 隔离校验
  -> 创建 Deployment Generation 1
  -> 发布 Route
  -> Worker 准备函数
  -> Gateway 发布 Serving Snapshot
```

调用链路是：

```text
HTTP 请求
  -> Gateway 认证与限流
  -> 查询 Serving Snapshot
  -> Route 选择
  -> Endpoint 选择
  -> Worker Fence 校验
  -> 创建 Guest Instance
  -> 执行 WASM
  -> 返回 HTTP 响应
```

### Q70：函数编译后为什么不能直接执行？

**参考回答：**

编译成功只说明文件生成了，不说明平台一定能安全运行它，所以还要做一次上线前检查。

编译完成只代表得到了一个 WASM 文件，不代表它符合平台的 ABI、安全和运行时约束。

上传后还需要检查 Artifact Digest、WASI 导入、`_start` 入口、内存限制、Runtime Feature Profile 和编译兼容性。只有 Validator 通过后，Version 才能进入 Ready，并进一步创建 Deployment。

### Q71：上传 Artifact 后，平台内部保存什么？

**参考回答：**

平台保存的是 WASM 文件本身和它的指纹、大小、运行环境等信息，之后通过指纹找到这份固定文件。

平台保存的是内容寻址的 WASM 二进制，以及与它关联的 Digest、大小、ABI、Runtime Profile 和版本元数据。

Version 不依赖用户本地文件名，而是通过 SHA-256 Digest 引用不可变 Artifact。这样可以保证同一个 Version 在不同时间加载到的是同一份内容。

### Q72：Version、Deployment 和 Route 的先后关系是什么？

**参考回答：**

顺序就是“先有代码版本，再准备怎么运行，最后决定流量发给谁”。未检查、未准备好的版本不能直接接收请求。

先创建不可变 Version，再通过 Validator 校验；校验成功后创建 Deployment Generation 1；最后 Route 才能把流量指向这个 Ready Version。

Route 不能直接指向一个还没有完成校验或部署准备的 Version，否则 Gateway 可能发现路由存在，但 Worker 实际无法执行。

### Q73：Worker 在调用前具体做了什么？

**参考回答：**

Worker 在真正接请求前，要确认文件没被替换、运行环境匹配、函数已经准备好，并且当前 Worker 确实被授权执行它。

Worker 会重新打开并校验 Artifact，检查实际字节和 Digest 是否匹配，然后使用正确的 Runtime Profile 编译模块，并将 Compiled Module 放入缓存。

之后 Worker Agent 创建 Ready Replica，安装与当前 Worker Session、Assignment、Version 和 Deployment Generation 匹配的 Serving Authorization。只有这些状态都准备好后，Endpoint 才会被发布到 Serving Snapshot。

### Q74：客户端调用发布后的函数时，客户端需要知道 WASM 吗？

**参考回答：**

不需要。对客户端来说，它就是一个普通 HTTP API，只要知道地址、请求格式和认证信息即可。

不需要。客户端只需要知道函数的 HTTP URL、请求格式和认证信息。

例如：

```bash
curl -X POST \\
  http://127.0.0.1:8080/invoke/text-clean \\
  -H 'Content-Type: text/plain' \\
  -d '  hello    world  '
```

客户端不需要安装 Go、Wazero 或 WASM 文件。Gateway 会把 HTTP 请求转换为项目定义的 WASI Command Request，再交给 Worker 执行。

### Q75：WASM 函数是如何返回 HTTP 响应的？

**参考回答：**

函数本身不需要监听 HTTP 端口。Gateway 把 HTTP 请求翻译成标准输入，函数把结果写到标准输出，Gateway 再翻译回 HTTP 响应。

函数通过标准输入读取 Request Envelope，通过标准输出写入 Response Envelope。Gateway 负责把 HTTP Method、Path、Query、Headers、Body 和 Deadline 编码进 Request，再把函数返回的 Status、Headers 和 Body 解码为 HTTP 响应。

例如：

```text
HTTP Body: "  hello    world  "
  -> WASM Request Envelope
  -> 函数清洗文本
  -> WASM Response Envelope
  -> HTTP Body: "hello world"
```

### Q76：完整链路中有哪些关键失败点？

**参考回答：**

可以把这些失败理解为平台在不同关口主动刹车：文件不对不发布，版本没准备好不路由，权限过期不执行，资源超限就停止调用。

常见失败路径包括：

- WASM 格式或 ABI 不合法：Version 进入 `Failed`。
- Artifact Digest 不匹配：拒绝上传或拒绝 Worker 加载。
- Version 尚未 Ready：Route 不允许指向它。
- Deployment Policy 不匹配：Worker 不发布 Ready Replica。
- Worker Session 过期：Fence 校验失败，拒绝执行。
- Token 认证失败：Gateway 在调用 Worker 前拒绝请求。
- 请求或响应超限：返回稳定的资源限制错误。
- 函数超时或异常退出：销毁当前 Guest Instance，释放资源并返回执行错误。
- Resource Revision 过期：CAS 拒绝更新，避免覆盖新状态。

设计这些失败路径的目的，是让系统宁可拒绝调用，也不执行身份、版本或策略不明确的函数。

## 十五、调用方与平台方的职责

### Q77：函数开发者需要负责什么？

**参考回答：**

开发者只需要负责业务代码、输入输出约定和编译结果；平台相关的进程管理和资源回收由平台负责。

开发者主要负责：

- 编写函数业务逻辑
- 遵守 WASI Command ABI
- 定义输入和输出格式
- 控制函数本身的执行时间和数据规模
- 编译出符合平台 Runtime Profile 的 WASM

开发者不需要负责 HTTP 监听、Worker 进程、Guest Instance 创建、编译缓存和函数资源回收。

### Q78：平台负责什么？

**参考回答：**

平台负责把函数从一个文件变成可被安全调用的服务，包括发布、路由、执行和故障处理。

平台负责：

- Artifact 上传和摘要校验
- Version 和 Deployment 生命周期
- Validator 隔离校验
- Route 和 Serving Snapshot
- Worker 准备和调用
- 认证、限流和超时
- WASM Instance 创建和销毁
- 失败状态和资源释放

这就是 Serverless 的核心：开发者提交函数逻辑，平台管理函数运行环境。

### Q79：使用者调用函数时需要安装项目吗？

**参考回答：**

不需要。调用者只要能访问 URL，就像调用普通接口一样使用，不需要安装 WASM、Go 或 Wazero。

不需要。只要能访问平台的 HTTP 地址，任何支持 HTTP 的客户端都可以调用，包括浏览器、curl、Go、Java、Python、JavaScript 或其他服务。

调用方不需要理解 WASM，也不需要拥有函数源代码。

## 十六、本机直接调用与平台调用的取舍

### Q80：如果函数和调用方都在同一台电脑，为什么不直接调用 Go 函数？

**参考回答：**

如果只是本机内部、可信代码之间的高频调用，直接调用 Go 函数确实更快。MiniCloud 的价值是把函数独立发布，方便隔离、跨程序复用和远程调用。

如果是同一个项目中的可信代码，并且追求最低延迟，直接函数调用更好：没有 HTTP、序列化和 WASM Instance 创建开销。

MiniCloud 的优势不在本机单次调用性能，而在于它提供了独立发布、版本管理、跨语言调用、资源限制和代码隔离。

因此：

- 工具函数、内部算法和高频计算：直接函数调用更合适。
- 独立插件、动态更新函数、不可信代码和跨项目复用：平台调用更合适。

### Q81：为什么不把所有功能都写在一个 Gin 服务里？

**参考回答：**

Gin 和 MiniCloud 都可以通过 HTTP 调用，但 Gin 是自己维护一个长期运行的完整服务；MiniCloud 是上传独立函数，由平台按调用运行。

Gin 适合构建长期运行的 HTTP 服务。所有功能可以注册成不同路由，但这些功能通常共享同一个进程、依赖和资源边界。

MiniCloud 把函数作为独立制品管理，每个函数可以独立发布和校验，调用时创建新的 Guest Instance，并由平台统一处理超时、限流和资源回收。

所以二者的调用形式都可以是 HTTP，但运行模型不同：Gin 是长期运行的服务，MiniCloud 是按调用执行的函数。

## 十七、性能与工程取舍

### Q82：使用 WASM 函数会不会比直接调用慢？

**参考回答：**

会有额外开销，因为多了 HTTP、编解码、权限检查和实例创建。它换来的不是更快，而是隔离、独立发布和跨机器调用。

单次本地调用通常会更慢，因为需要经过 HTTP、ABI 编解码、路由、授权和 Guest Instance 创建。项目通过编译模块缓存减少重复编译成本，但不会把 Guest Instance 状态跨调用复用。

因此这个平台优化的重点不是替代同进程函数调用，而是以可接受的运行开销换取隔离、可部署性、版本管理和跨机器调用能力。

### Q83：为什么不为了性能复用 Guest Instance？

**参考回答：**

复用实例虽然可能更快，但容易把上一个请求的数据带到下一个请求，还会让并发和异常恢复变复杂。MVP 优先保证每次请求互不影响。

复用 Guest Instance 可能带来更低的实例化开销，但会引入全局变量、内存、连接和请求状态泄漏的问题，也需要处理并发重入和异常恢复。

MVP 优先保证请求隔离和状态可预测性，因此复用的是只读 Compiled Module，不复用 Guest Instance。

### Q84：这个平台最适合什么样的函数？

**参考回答：**

最适合“小、短、独立、输入输出明确”的函数；不适合长期保持连接或依赖大量本地状态的完整服务。

最适合输入输出边界清晰、执行时间有限、可以无状态运行的函数，例如文本处理、格式转换、Webhook、请求校验、图片处理、规则判断和边缘数据转换。

不适合长期持有连接、依赖大量本地状态、需要复杂事务或必须持续运行的服务。此类场景更适合传统 HTTP 服务、gRPC 服务或容器化应用。

## 十四、管理面 API 与写操作幂等实现

### Q85：管理 API 如何保证"响应丢失后重试"是安全的？

**参考回答：**

通俗地说，客户端重复点击或网络超时重试时，平台要能认出这是同一个操作，不能重复创建资源。

每个管理写请求都必须携带 `X-Minicloud-Operation-Id` 头。服务端以 `{principal, namespace, operation_id}` 为作用域，把请求的规范摘要（方法、规范路径、CAS 前置条件、严格 JSON 请求体、Artifact Digest）与最终结果一起写入操作账本。

客户端超时后用同一个 Operation ID 重试：请求摘要相同则直接返回第一次的结果，不会执行第二次状态变更；摘要不同说明 ID 被复用，返回 `conflict`。客户端也可以直接 `GET /v1/operations/{id}` 查询结果，覆盖 "结果未知" 的场景。

### Q86：操作记录和资源变更如何做到原子？

**参考回答：**

核心要求是：要么资源变更和操作记录一起成功，要么两者都不要留下半成品，不能出现“资源已经改了但重试不知道”这种情况。

这是管理面最关键的设计约束：先写资源再写账本，账本写入失败会导致资源无法被重试识别；反过来先写账本，资源变更失败则账本记录了一次从未发生的变更。

项目的做法是把每个管理写拆成"准备"和"应用"两个阶段：所有可能失败的输入（ID 生成、命令元数据、Artifact 校验、容量检查）都在准备阶段完成；应用阶段只剩一个必然可判定的纯状态转换，由账本的 `CompleteAfter` 在同一个临界区内先校验重放和容量，再执行状态变更，最后插入终态记录。

### Q87：Version 创建为什么不把校验结果算进操作结果？

**参考回答：**

因为创建版本和验证文件是两个阶段。创建版本可以先成功，验证服务稍后再完成；验证服务临时故障时，不会把创建操作误判成失败。

Validator 是独立子进程，可能出现临时性基础设施故障。这种失败既不是成功也不是终态失败，而账本只能存终态结果。

因此操作边界只覆盖"创建不可变 Uploaded Version"这一步；校验在操作提交后异步驱动，临时失败留下持久化的验证围栏，由收敛循环重试。客户端重试同一个 Operation ID 会拿回同一个 Version，然后轮询它的状态直到 Ready 或 Failed。这也是 M1 Raft FSM 中"持久化 pending 意图"设计的单进程前身。

### Q88：一次性凭据为什么不能重放？细节是什么？

**参考回答：**

一次性凭据就像只显示一次的密码。第一次响应丢失后不能从账本里再次读取明文，而是重新申请新凭据，避免秘密长期留在系统里。

创建 Token 函数或轮换 Invocation Token 时，明文只在第一次响应中返回，账本只记录"发过凭据"这个布尔标记和资源标识，绝不存明文。

重试相同 Operation ID 时返回 `credential_not_replayable`（HTTP 409），`details` 里带资源 ID 和当前 Resource Revision。客户端此时的正确动作不是继续重试，而是调用轮换接口拿一个新凭据。这样即使响应丢失，凭据也不会进入任何持久状态或日志。

### Q89：路由发布之后，副本是怎么被放置到 Worker 上的？

**参考回答：**

发布 Route 只是宣布“希望流量去哪个版本”，不等于 Worker 已经准备好。平台还要先决定放在哪个 Worker，再准备副本，最后才加入可调用清单。

发布 Route 只是提交了期望状态。Local Core 的收敛循环里有一个放置步骤：对每个有已启用 Route 的 Function，比较当前的 Assignment 意图和 Route Target；缺少放置时用确定性 Planner 在单个本地 Worker 上做一次选择，并以 Deployment Scaling Revision CAS 提交 Assignment 意图。

Reconciler 观察到已提交的意图后才准备 Replica、安装授权，最后由 Serving Synchronizer 发布完整快照。这保持了"先提交意图、再执行副作用"的顺序约束。Route 切换到新 Version 时，旧 Assignment 先按 CAS 取消，下一轮收敛再放置新目标，避免新旧 Replica 抢占资源。

### Q90：管理面和调用面为什么用两个监听地址？

**参考回答：**

管理面可以创建和修改资源，权限更高；调用面只负责执行函数。分开后可以分别设置网络暴露范围，降低管理接口被外部访问的风险。

两个入口的信任模型完全不同：管理面持有静态管理员 Token，可以创建函数和轮换凭据；调用面只按每个函数的 Trigger 策略认证。分开监听后可以独立绑定地址、独立配置 TLS，比如管理面只绑回环、调用面对外暴露。

管理 Token 的摘要用常量时间比较，认证主体是独立配置的 `admin_subject`，而不是 Token 本身的摘要——这样带外替换 Token 不会改变操作幂等的去重身份。
